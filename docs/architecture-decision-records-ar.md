## ADR-001 — PostgreSQL قاعدة بيانات واحدة لكل النظام

| الحقل | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** |
| **السياق** | النظام يخدم **ثلاث شركات مُدارة** (الروضة · الأقصى · الأمل) وشركات خارجية. والسؤال: **قاعدة لكل شركة أم قاعدة واحدة؟** والبيانات المشتركة كبيرة: الأطراف · المواقع · موارد التكلفة · البيانات المرجعية. |
| **القرار** | ⭐ **PostgreSQL واحدة لكل النظام.** ⛔ **لا قاعدة لكل شركة ولا لكل وحدة.** ونطاق الشركة يُمثَّل بـ**`managed_company_id` على المستندات والحسابات التي تحتاجه — ⛔ لا على كل جدول**. |
| **البدائل** | **أ) قاعدة لكل شركة** ⟹ ❌ **رُفضت**: الأطراف والمواقع وموارد التكلفة **مشتركة فعلًا**، وتكرارها يُنتج هويات متعددة للشخص الواحد — **وهو بالضبط العيب البنيوي الأول الذي نحله**. · **ب) Multi-tenancy بمفتاح على كل جدول** ⟹ ❌ **رُفض**: تعقيد بلا حاجة، **والشركات الخارجية `parties` لا Tenants**. |
| **المزايا** | ⭐ **هوية واحدة للطرف عبر كل الشركات** · تقارير مجمَّعة بلا دمج · نسخ احتياطي واحد · ⛔ **ولا مزامنة بين قواعد** |
| **التكلفة** | الحاجة إلى **ضبط النطاق بعناية** على المستندات المالية · وحجم قاعدة أكبر |
| **المخاطر** | **تسرب بيانات بين الشركات** إن أُغفل `managed_company_id` ⟹ **الضابط: فحص النطاق في مراجعة التصميم** |
| **النتائج** | `managed_company_id` على: المستخلصات · أوامر الدفع · القيود · الحسابات المالية · الضمانات · التسويات · كشوف الأجور · حسابات العهدة · التقارير. ⛔ **وليس على**: الأطراف · المواقع · موارد التكلفة · البيانات المرجعية |
| **المتطلبات** | FR-009 · NFR-SEC-009 |
| **تاريخ الاعتماد** | **قبل هذه الوثيقة** — مثبَّت في BR-156 |
| **من اعتمد** | **صاحب المشروع** |

## ADR-002 — Modular Monolith لا Microservices

| الحقل | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** |
| **السياق** | النظام يغطي **18 مجالًا** و**125 كيانًا** و**23 وحدة منطقية**، ويعمل عليه **فريق صغير**. والمعاملات المالية **تعبر الوحدات كثيرًا**: اعتماد مصروف يمس العهدة والتكلفة والتدقيق **في معاملة واحدة**. |
| **القرار** | ⭐ **Modular Monolith** — الوحدات منفصلة **منطقيًا**: لكل وحدة **حدودها وواجهتها وأحداثها**، و⛔ **لا تقرأ وحدة جداول وحدة أخرى مباشرة**. ويجوز استخدام **PostgreSQL schemas** لفرض الحدود على مستوى الصلاحيات — **قرار التصميم الفيزيائي**. |
| **البدائل** | **أ) Microservices** ⟹ ❌ **رُفضت قطعًا**: ⭐ **تجعل ذرّية المعاملة المالية وحدث التدقيق (BR-186) شبه مستحيلة** — وتتطلب Saga وتعويضًا، **وهو ما يفتح بالضبط الباب الذي يغلقه BR-186**. · **ب) Monolith بلا حدود** ⟹ ❌ **رُفض**: يُنتج تشابكًا يستحيل صيانته عند 125 كيانًا. |
| **المزايا** | ⭐ **معاملة واحدة تضمن الذرّية** · نشر بسيط · تشخيص أسهل · تكلفة بنية تحتية أقل · **وحدود منطقية تسمح بالانفصال لاحقًا إن لزم** |
| **التكلفة** | **انضباط الفريق مطلوب** لئلا تُخترق الحدود · ونشر واحد لكل تغيير |
| **المخاطر** | **اختراق الحدود مع الوقت** ⟹ **الضابط: PostgreSQL schemas + مراجعة كود** |
| **النتائج** | 23 وحدة موثَّقة بما تملك وما لا تملك · و**بوابة واحدة لكل نوع تكلفة** (BR-105) |
| **المتطلبات** | NFR-OPS-011 · NFR-OPS-013 · NFR-REL-001 |
| **تاريخ الاعتماد** | **قبل هذه الوثيقة** — BR-157 |
| **من اعتمد** | **صاحب المشروع** |

## ADR-005 — Private File Storage خارج قاعدة البيانات

| الحقل | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** |
| **السياق** | النظام ينتج **تقارير PDF شهرية بإصدارات متعددة لكل شركة**، ويقبل **مرفقات مصروفات ومستندات عقود**. والسؤال: **أين تُخزَّن؟** |
| **القرار** | ⭐ **الملف يُحفظ في Private File Storage خارج قاعدة البيانات.** والقاعدة تحفظ: **سجل الملف · الـLabel · مرجع التخزين · الميتاداتا · البصمة SHA-256 · الحجم**. و⛔ **لا Public URL دائم** · **وكل وصول يمر بفحص الصلاحيات** · **والرابط إن استُخدم مؤقت المدة ومرتبط بالمستخدم**. |
| **البدائل** | ⭐ **تخزين الـBinary داخل PostgreSQL** ⟹ ❌ **رُفض — بأربعة آثار موثَّقة**: **(1) حجم القاعدة** ينمو بمعدل حجم كل تقرير × عدد الإصدارات × عدد الشركات · **(2) النسخ الاحتياطية** تحمل كل الملفات ⟹ زمن أطول ومساحة أكبر · **(3) الاسترجاع** أبطأ **واسترجاع ملف واحد غير عملي** · **(4) الأداء** ضغط على الذاكرة المؤقتة والإدخال/الإخراج. ⭐ **ويُذكر البديل بوصفه غير موصى به، ولا يُعتمد إلا بقرار صريح يقبل الآثار الأربعة** (BR-233). |
| **المزايا** | ⭐ **قاعدة بيانات نظيفة وسريعة** · **نسخ احتياطي منفصل** · **استرجاع انتقائي** |
| **التكلفة** | **اعتمادية خارجية** (DEP-02) · **واتساق بين القاعدة والتخزين** |
| **المخاطر** | **فقد الملف مع بقاء سجله** ⟹ **الضابط: SHA-498 ونسخ احتياطي منفصل ومطابقة دورية** |
| **النتائج** | ⭐ **الملف والـSnapshot يُحفظان قبل أي محاولة إرسال** (BR-242) · ⛔ **ولا محتوى ملف في أي سجل** |
| **المتطلبات** | FR-REP-013 · FR-REP-014 · NFR-SEC-004 · NFR-OPS-005 |
| **تاريخ الاعتماد** | **قبل هذه الوثيقة** — BR-232 · BR-233 |
| **من اعتمد** | **صاحب المشروع** |

## ADR-006 — سجل تدقيق مالي منفصل عن Serilog

| الحقل | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted — ⛔ ولا يُعاد فتحه** |
| **السياق** | ⭐ **السؤال الرقابي الأول في أي نظام مالي: من فعل ماذا ومتى ولماذا؟** والإغراء الطبيعي: **استخدام سجلات التطبيق (Serilog) لهذا الغرض** لأنها موجودة بالفعل. |
| **القرار** | ⭐ **ثلاثة أنظمة منفصلة إلزاميًا**: **(أ) الدفاتر والقيود** — ⭐ **المصدر الوحيد لأي رقم** · **(ب) سجل التدقيق المالي** — **من فعل ماذا ومتى ولماذا** · **(ج) Serilog** — **تشخيص تقني**. و⭐ **حدث التدقيق يُكتب داخل نفس معاملة العملية، وفشله يُفشلها ويحدث Rollback** · بينما ⭐ **فشل إرسال Serilog لا يُفسد معاملة ناجحة — عكسه عمدًا**. |
| **البدائل** | **أ) Serilog كسجل تدقيق** ⟹ ❌ **رُفض**: **نجاحه احتمالي** — والوجهة خارجية والملف قابل للتدوير، ⭐ **فالعملية المالية قد تنجح بلا أثر تدقيق = عملية بلا مسؤول**. · **ب) أعمدة تدقيق داخل جداول العمل** ⟹ ❌ **رُفض**: ⛔ **لا تُثبت من حاول وفشل، ولا تشرح المعنى التجاري، وتتضخم بلا حدود**. · **ج) طابور خارجي للتدقيق** ⟹ ❌ **رُفض**: **يجعل نجاح التدقيق احتماليًا** — وهو بالضبط ما يمنعه القرار. |
| **المزايا** | ⭐ **ألا توجد حركة مالية بلا مسؤول** · **Append-only لا يقبل التعديل ولا الحذف ولا للأدمن** · **وفصل واضح للصلاحيات: الفريق التقني لا يصل إلى محتوى الأحداث المالية** |
| **التكلفة** | ⭐ **كتابة إضافية في كل معاملة مالية** · وحجم تخزين متنامٍ · **وأداء أبطأ قليلًا** |
| **المخاطر** | **تضخم الحجم وتأثيره على الأداء** (RISK-006) ⟹ **الضابط: سياسة احتفاظ متدرجة وأرشفة — والضبط الفني في التصميم الفيزيائي** · و**الالتفاف بكتابة حدث زائف** (RISK-009) ⟹ ⛔ **منع صريح: التصحيح بحركة لا بسجل** |
| **النتائج** | **مستويان إلزاميان معًا** (تدقيق عام + أحداث أعمال صريحة) · **12 مجموعة أحداث حد أدنى** · **96 حدثًا موثَّقًا** · **وسجل إرسال التقرير سجل رابع مستقل** |
| **المتطلبات** | FR-AUD-001 … FR-AUD-018 · NFR-REL-001 · NFR-REL-006 |
| **تاريخ الاعتماد** | **قرار معماري ورقابي** — Patch 1.1.2 |
| **من اعتمد** | **صاحب المشروع** |

## ADR-007 — التصحيحات المالية Append-only

| الحقل | المحتوى |

## ADR-016 — Party Model موحَّد بلا Multi-tenancy

| الحقل | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** |
| **السياق** | ⭐ **الشخص الواحد قد يكون عاملًا وموردًا ومدينًا في آن.** والشركة قد تكون **صاحبة ورق ومنفّذة ومستفيدة اقتصاديًا** على عمليات مختلفة. **والواقع القديم: أسماء نصية في ستة أعمدة مختلفة.** |
| **القرار** | ⭐ **Party Model موحَّد**: `parties` هوية مركزية · `party_roles` أدوار **مؤرَّخة** · `party_aliases` تهجئات · `party_identifiers` معرّفات **بنطاقها** · `party_accounts` حسابات فرعية · `operation_party_roles` **أدوار على عملية بعينها**. و⭐ **«شركاتنا» علاقة ملكية/إدارة مؤرَّخة على `parties` لا جدول هوية منفصل** · و⭐ **الشركات الخارجية `parties` لا Tenants**. ⭐ **والواجهة تعرض شاشات مألوفة ولا تُجبر المستخدم على مصطلح Party.** |
| **البدائل** | **أ) جداول منفصلة لكل دور** (عمال · موردون · مقاولون) ⟹ ❌ **رُفضت**: ⭐ **الشخص الواحد بأدوار متعددة يتكرر، ويصبح «كم على فلان؟» سؤالًا بلا إجابة**. · **ب) Party Model بلا شاشات مألوفة** ⟹ ❌ **رُفض**: ⭐ **يُربك المستخدم بمصطلح تقني لا يعنيه**. · **ج) Multi-tenancy للشركات الخارجية** ⟹ ❌ **رُفض**: **الشركة الخارجية طرف نتعامل معه لا مستأجر للنظام**. |

## ADR-017 — كشف التشابه بدل قيود التفرّد على الأسماء

| الحقل | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** |
| **السياق** | ⭐ **تشابه الأسماء في مصر شائع.** والإغراء الطبيعي: **فرض `UNIQUE` على الاسم المطبَّع لمنع التكرار**. ⭐ **والدليل المرصود:** `عمال حسين القناوى` مقابل `عمال حسين قناوى خوارج` — **قد يكونان موردين مختلفين فعلًا** («خوارج» = عمالة من خارج الموقع) **أو خطأ إملائيًا**. |
| **القرار** | ⭐ ⛔ **لا `UNIQUE` على الاسم المطبَّع ولا على الاسم البديل عالميًا.** ⭐ **والتفرّد يُبنى على المعرّفات الرسمية عند توفرها.** ⭐ **وما عداه: كشف تشابه ينتج مرشّحًا للمراجعة البشرية — ينبّه ولا يدمج ولا يمنع الإنشاء.** |
| **البدائل** | **أ) `UNIQUE` على الاسم المطبَّع** ⟹ ❌ **رُفض قطعًا**: ⭐ **كان سيدمج شخصين حقيقيين — وفقد الهوية أخطر من تكرارها، لأن التكرار يُكتشف والدمج لا يُكتشف**. · **ب) دمج آلي عند تجاوز عتبة تشابه** ⟹ ❌ **رُفض**: ⭐ **الدمج قرار بشري دائمًا**. |
| **المزايا** | ⭐ **لا فقد هوية** · **والمراجعة البشرية تحسم ما لا تحسمه الخوارزمية** |
| **التكلفة** | ⭐ **عبء مراجعة بشرية** · واحتمال بقاء تكرار حتى تُحسم المراجعة |
| **المخاطر** | **تراكم مرشحين بلا مراجعة** ⟹ **الضابط: تنبيه عند إنشاء مرشّح جديد وتقرير للمرشحين المفتوحين** |
| **النتائج** | **`party_similarity_candidates`** بحالات `Open` · `Merged` · `Rejected` · `Deferred` · **والمؤشرات: اسم مطبَّع · معرّف جزئي · حساب بنكي · بصمة تسوية · حركة شبه مكررة · صافي سالب** · ⭐ **وهو الطبقة السابعة من طبقات منع الازدواج** |
| **المتطلبات** | FR-004 · FR-005 · FR-SUP-010 · FR-WRK-018 |
| **تاريخ الاعتماد** | **قبل هذه الوثيقة** — BR-100 · BR-106 · BR-168 |

## ADR-018 — Idempotency Key مدخلًا إلزاميًا لكل مصدر خارجي

| الحقل | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** |
| **السياق** | ⭐ **أربعة مصادر تُنتج أثرًا ماليًا من خارج جلسة المستخدم**: **المزامنة بلا إنترنت · الاستيراد التاريخي · المهام الخلفية · إعادة إرسال الطلب عند ضعف الشبكة**. ⭐ **وكلها قابلة للتكرار بطبيعتها.** |
| **القرار** | ⭐ **كل مدخل خارجي يحمل `Idempotency Key` أو `Client Event ID`**، ⭐ **وتكراره بنفس المفتاح لا يُنشئ معاملة مالية ولا حدث تدقيق مكررًا**. ⭐ **وهذا — لا تفرّد المصدر — هو خط الدفاع ضد الترحيل المكرر.** |
| **البدائل** | **أ) تفرّد على بيانات المصدر** (مورد + موقع + تاريخ) ⟹ ❌ **رُفض**: ⭐ **يمنع حركات صحيحة** — وردية ثانية · فئتا أجر · تصحيح سطر. · **ب) كشف تكرار بعدي** ⟹ ❌ **رُفض وحده**: **يكتشف بعد وقوع الأثر المالي**. · **ج) `line_number` مفتاحًا** ⟹ ❌ **رُفض**: ⭐ **رقم عرض لا هوية — وإعادة إرسال السطر نفسه تمرّ بمجرد تغيّر ترتيبه**. |
| **المزايا** | ⭐ **منع الأثر المزدوج قبل وقوعه** · ⛔ **بلا منع أي حركة صحيحة** · **ويعمل مع كل المصادر الأربعة بمبدأ واحد** |

| **المتطلبات** | FR-EXP-019 · FR-IMP-005 · FR-REP-022 · FR-AUD-004 · NFR-REL-002 |
| **تاريخ الاعتماد** | **قبل هذه الوثيقة** — BR-103 · BR-188 · BR-241 |

## ADR-028 — ⭐ قيد واحد لكل حدث مالي

| البند | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** — 2026-09-20 |
| **السياق** | **`UNIQUE(financial_event_id, entry_type, posting_sequence)` كان يسمح بعدة قيود للحدث الواحد** |
| **القرار** | ⭐ **`Financial Event 1 : 0..1 Journal Entry`** · **و`1 : 1` إلزامية بعد `Posted`** · ⛔ **و`posting_sequence` أُلغي** |
| **لماذا** | ⭐ **القيد الواحد يحتمل سطورًا متعددة** — **فلا حاجة لقيود متعددة** · ⛔ **وتعدد القيود على الحدث يفتح باب قيد ثانٍ بلا سند ويصعّب المطابقة** |
| **البديل عند الحاجة لأثر إضافي** | ⭐ **حدث مالي مستقل بقيده المستقل** — **والعكس حدث مستقل يشير إلى أصله** |
| **الملغى** | ⛔ `source_type` · `source_id` · `posting_event` · `posting_sequence` **من `journal_entries`** |

## ADR-029 — ⭐ `accounting_adjustments` مستندًا رسميًا لكل تصحيح

| البند | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** — 2026-09-20 |
| **السياق** | **العكس المالي كان بلا مستند معتمَد** — ⛔ **فيصبح تعديلًا صامتًا لا يُراجَع** |
| **القرار** | ⭐ **كيان واحد جديد** يغطي: `OpeningBalance` · `Correction` · `Reclassification` · `ManualAdjustment` |
| **البدائل المرفوضة** | ⛔ **حقل «سبب» على القيد** ❌ — **لا يحمل مسار اعتماد ولا يربط حدثين** · ⛔ **كيان لكل نوع تصحيح** ❌ — **أربعة كيانات بنفس الحقول** |
| **القواعد** | ⛔ **لا ترحيل قبل الاعتماد** · ⛔ **لا تعديل بعد الترحيل** · ⭐ **والاستبدال = حدث عكس + حدث صحيح تحت المستند نفسه** |
| **النطاق** | ⭐ **W1-D · MVP Required** — **لأن التصحيح الآمن شرط تشغيلي لا رفاهية** |

## ADR-031 — ⭐ `settlement_mode` و`instrument`

| البند | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** — 2026-09-20 |
| **القرار** | ⭐ **`funding_source` ⟸ `settlement_mode`** بأربع قيم: **`Custody` · `Treasury` · `OnAccount` · `NonCash`** |
| **لماذا الاسم الجديد** | **«مصدر التمويل» يوحي باختيار المستخدم** — ⭐ **بينما المقصود: كيف سُوِّي الأثر ماليًا، وهي نتيجة مسار الاعتماد لا إدخال** |
| **`instrument`** | ⭐ **إلزامي في الحركات النقدية الفعلية فقط** · **بقواعد شرطية لكل قيمة** · ✅ **ويجوز فارغًا مع الرصيد الافتتاحي والتسويات وغير النقدي** |
| ⛔ **الحد الصارم** | ⛔ **لا `settlement_mode` ولا `instrument` ولا طريقة دفع في واجهة المهندس** — **يحددها النظام** |

## ADR-032 — ⭐ استراتيجية استيراد البيانات التاريخية

| البند | المحتوى |
|---|---|
| **الحالة** | ✅ **Accepted** — 2026-09-20 |
| **السياق** | **قاعدة «قيد واحد لكل دفعة استيراد» مختزِلة** — ⛔ **تفقد أبعاد العملية والموقع والطرف والشهر** |
