# Contractra — Master Roadmap and Sprint Plan

**Kind:** working document under `docs/implementation/**` (precedence and the map of files: `docs/implementation/README.md`). It is the **single** project-wide plan; sprint files (`backend/sprints/sprint-NN.md`) hold the detailed stories and tasks of one sprint and must point here rather than copy it.
**Written:** 2026-10-21 · **Basis:** Git `backend/users-slice-7` @ `1644077`, `main` @ `fb45c1d`, both frontend worktrees @ `fb45c1d` (see §1).
**Corrected 2026-10-22 (fourth pass):** the retry design is fixed. The earlier text generated a new password on every delivery attempt, so a delayed message could arrive after a retry had replaced the stored hash. **One password is now generated per operation (creation or reset), its hash is stored with the operation, and retries send the same password from a short-lived encrypted copy in the delivery outbox** (plan §1F.3–§1F.4; contract §23). It is the recommended design; production key custody and the owner's acceptance of an encrypted copy at rest are open (OD-30), as is what a reset invalidates while delivery is pending (OD-29). No code exists for any of it.
**Revised 2026-10-21 (third pass):** the owner **confirmed** (R49–R51) that the system generates the employee's password and sends the username and password to the employee's WhatsApp, with no forced password change, for both account creation and reset, using the official Meta WhatsApp Cloud API with English-only usernames suggested from the name. This **supersedes** R48 (temporary password shown to the Admin) and **withdraws and removes** the activation-link proposal (PW-2) from the second pass. Sections changed: §3 (rewritten), §4 (OD-1/OD-2 reworded; OD-16/17/24 closed; OD-18–OD-23 reworded; OD-25–OD-28 added), §7 PS-03 (now decisions, design and frontend foundation — no backend credential code), PS-04a/PS-04b (rewritten), matrix, risks, handoff. ## 3. Credential policy — confirmed owner decisions R49–R51 (2026-10-21)

**Status: CONFIRMED by the owner (2026-10-21); planning only — nothing is implemented.** Full text, supersession table, design and limitations: `backend/features/admin-user-creation-plan.md` §1F; contract shapes: `auth-and-users-api-contract.md` §23. R49–R51 were numbered by planning; the owner may renumber.

| # | Decision in one line |
|---|---|
| **R49** | New employee account: Contractra generates a strong random initial password; the English-only username is suggested from the name and is Admin-editable; after creation Contractra **automatically sends the username and password to the employee's WhatsApp**; changing the password after first sign-in is **optional** (no forced change). |
| **R50** | Reset: Contractra generates a new strong random password and **automatically sends the username and new password to the employee's WhatsApp**; changing it is **optional**; any reset flow that forces a change is removed. |
| **R51** | Delivery: official **Meta WhatsApp Cloud API**; delivery status recorded; safe retry/resend; a WhatsApp failure never silently loses an account creation or a reset; number validation, consent/opt-in, approved template, webhook verification, retry/idempotency, configuration and failure handling documented; the password is never logged, never in audit, errors or ordinary API responses, and **never stored in plaintext**. Clarified 2026-10-22: the prohibition is on **plaintext**, not on encrypted-at-rest storage, so delivery uses **one password per operation, its hash in the user record and a short-lived encrypted copy in the outbox for same-password retries** (plan §1F.4), with the trade-offs of credentials over WhatsApp written down (§1F.6). |

**What this replaces.** R48 (temporary password shown to the Admin; forced change) and, in their credential parts, R1–R3, R16, E3, E4 and R44's reset-code design — superseded; the earlier same-day **activation-link proposal (PW-2) is withdrawn and removed** (no activation tokens, endpoints, states, screens or Employee web route). The Admin **no longer sees any password**. There is **no temporary-password fallback** for an Admin to hand over; recovery is a re-issue (OD-27 asks whether the owner wants any other fallback; default none).

**Final behaviour (summary of plan §1F.3)**
- *Create:* Admin supplies roles, Party (Engineers), name, WhatsApp number (entered twice) and the consent affirmation → server suggests an English username, Admin may edit → **one transaction** generates **one** password, stores **its hash** in the user record, **seals** the plaintext in the outbox row and writes the user (valid hash, nothing forced), the consent record, the issuance, the queued delivery and the audit → `201` with the delivery status, **no password** → a background worker opens the sealed copy only to send, sends it in the approved template and retries with the **same** password → the employee signs in; changing the password is optional.
- *Reset:* Admin requests → **one transaction** generates one new password, **replaces the user's hash**, revokes all sessions, bumps `security_version`, supersedes any earlier open issuance (its sealed copy purged) and queues the new one → `202` with the delivery status, **no password** → the worker delivers the same new password on every retry → optional change. **The old password and sessions are invalidated at request time; the employee cannot sign in until the new password arrives. Not a confirmed product decision (OD-29).**
- *Failure:* the account and the operation stay; the Admin sees `credentialState` (`PasswordSet`, `DeliveryPending`, `DeliveryFailed`) and the delivery status with a failure category; the safe recovery is a guarded **re-issue** (a new operation: new password, earlier issuance superseded, its copy purged). A delivery retry never changes the password; only a new operation or the employee's own change does. The sealed copy is purged at the earliest of delivery confirmation, first sign-in or change, terminal failure, supersession, or the retention deadline.

## 5. Sequencing logic

1. **Business dependency chain** (from the MVP matrix and SRS §8.2, §12): identity → parties → operations/sites/assignments → documents + **audit completion** → accounting/treasury → custody → expenses (capture → review/approval) → workers/payroll → suppliers → reports → commercial (claims, retentions) → import. The matrix states that no real financial movement may run before W1-C (documents, audit) and W1-D (accounting, treasury).
2. **Gate A** (ADR 0006 §8.3): no migration introducing a financial table or module until Audit Completion is implemented, tested, reviewed and approved. Sequencing consequence: Audit Completion (PS-07) precedes every financial sprint (PS-08 …). Operations/sites/assignments are not financial and may precede it, but need the audit context CHECKs relaxed first (§2.5).
3. **First useful end-to-end workflow: PS-04 — an Admin provisions an employee (Engineer) account and the employee signs in and signs in with the credentials delivered to their WhatsApp**, on real backend, in both apps. *(2026-10-21, R49–R51: the employee receives the username and a generated password on WhatsApp and may change it later; PS-04a delivers the whole workflow on a fake sender, so it never waits on Meta, and PS-04b adds the live Meta API.)* Why first: it is the only complete business flow whose backend is already built (Slices 1–7); it exercises the shared auth/networking core that every later feature in both apps depends on; it is a hard prerequisite of every Employee-app feature (no login, no app); it retires the mock-only frontend state, the largest unverified integration risk; and it needs no new financial design. The gap to close first is small and concrete: the credential-delivery design (§3, built in PS-04a) and the missing Party lookup (OD-4).
4. **First useful *financial* end-to-end flow: PS-11** — Engineer records and submits an expense against an assigned site; staff reviews and approves; the custody balance and operation cost reflect it, with audit. It is the SRS's "most used screen" (matrix W1-E) and cannot be reached earlier without violating Gate A and the W1-C/W1-D rule.
5. **Apps stay independent.** The Admin and Employee apps share only the networking/session/auth-data package `contractra_core` (alignment plan §2); each sprint lists tasks per app, and an app only gains screens for permissions its audience can hold (Admin: `Apps.Admin.Access`; Employee: `Apps.Employee.Access`, held today only by role `Engineer`).
6. **Detail decreases with distance.** PS-03 and PS-04 are executable now. PS-05 … PS-11 are fully scoped but each starts with a planning step that rechecks the sources and writes `backend/sprints/sprint-NN.md`. PS-12 onward are **provisional**: the order and boundaries are a recommendation and are re-confirmed when the preceding sprint closes (OD-14).

## 7. Sprint definitions

**Common Definition of Done (every sprint; sprint sections add to it):** the contract/spec section for the change is updated *before* the code; `dotnet build` 0 warnings / 0 errors; Domain + Application tests green; PostgreSQL-backed tests green on an **isolated** instance (never a development or shared database), with the instance and counts recorded; for each app `flutter analyze` clean and tests green with counts recorded; every authorization and audit rule has a test; no secret in code, logs, audit or responses; migrations additive, with a tested `Down` and no automatic application; sprint file written, status recorded in the sprint file with evidence; an acceptance review document for any slice the owner must accept; owner acceptance recorded before the sprint is called closed. ### PS-04 — First end-to-end workflow: provision an employee, deliver the credentials, first sign-in (PS-04a and PS-04b)

**Objective / value.** An Admin creates an employee (Engineer) account: they give the employee's name and WhatsApp number, accept or edit the suggested English username, and the system **generates a strong password and sends the username and password to the employee's WhatsApp** (R49); the employee signs in on the Employee app and reaches the empty home shell, with changing the password entirely optional. An Admin can reset the employee's password, which sends a new generated password the same way (R50). The Admin sees the delivery status and can safely re-issue (R51); no password is ever shown to the Admin. **Scope.** Party lookup/create (minimum for Engineer accounts); real-mode auth and users in both apps; the username policy and suggestions; credential issuance, outbox, delivery worker, webhook, re-issue, status and recovery; Admin and Employee changes; scripted end-to-end run; dev/runbook. **Exclusions:** full Party management (PS-05); role/permission assignment after creation (FR-AUTH-005, contract §15); assignments; any business screen; e-mail/SMS and any channel other than WhatsApp; user-initiated forgot-password; reset-code completion; **any activation link or employee-chosen-password flow (withdrawn)**; an in-band password fallback (OD-27); a forced or prompted password change; account deletion; a general notification system (W3); WhatsApp conversations or replies; bulk onboarding.
